# Deploy — التشغيل والنشر

مطابق لـ[workflow](../../.github/workflows/build-and-deploy.yml) و[scripts](../../scripts/monsterasp_ftps.py) و[ReleaseSafety](../../Payroll.Api/ReleaseSafety.cs)، بتاريخ 2026-10-26. هذه تعليمات تشغيل؛ لم يُنفذ نشر أو تراجع أو نسخ بيانات في مهمة التوثيق.

## الإذن وسلوك CI

أي نشر أو نشر عام يحتاج موافقة Ghazal الصريحة. دفع `main` يشغّل نشر الإنتاج تلقائيًا بعد الاختبارات؛ لذلك الدمج/الدفع إلى main إجراء نشر فعلي. لا تستنتج إذنًا حاليًا من إذن مذكور في تسليم تاريخي. مهمة knowledge pack: commit محلي بعنوان فيه `[skip ci]`، **بلا push**.

`pull_request` يشغّل التحقق والحزم. `workflow_dispatch` يشغّل التحقق والحزم أيضًا؛ خطوات النشر الحالية مشروطة بحدث `push` على `main`. لا يوجد الآن staging أو GitHub Environment بمراجع إلزامي، ولا rollback تلقائي. تزامن main لا يُلغى أثناء نشره؛ تشغيلات الفروع يمكن إلغاؤها عند وصول رأس أحدث.

## البناء والاختبارات

المتطلبات: .NET SDK 10، Node.js 24، npm، وPython 3. CI يثبّت TypeScript من lockfile، ويستخدم Chromium مع Playwright. من جذر المستودع:

```bash
npm ci --no-audit --no-fund --prefix RiderForm
dotnet build tests/Engine.Tests -v q
dotnet run --no-build --project tests/Engine.Tests -- --accounting-review
dotnet test tests/Engine.Tests --no-build
python3 -m unittest discover -s scripts -p 'test_*.py' -v
```

الاختبار offline يغطي المحاسبة ومحرك الحساب دون HTTP/browser/SQL Server. MSTest الكامل قد يتطلب TCP محليًا، وستُتخطى اختبارات SQL Server إن لم تجهز خدمته؛ لا تسوّق نجاح subset كنجاح لكل المزودات. في CI توجد خدمة SQL Server ومجموعات HTTP لكل من SQLite وSQL Server.

سير CI الحالي:

1. preflight للاتصال والشهادة قراءة فقط على دفع main، دون إيقاف الموقع.
2. تثبيت الاعتماديات وجلب الخطوط المثبتة، ثم فحص حدود source bundle واختبارات أدوات النشر.
3. تشغيل MSTest، وبناء API وأداة StoreMigration، ثم اختبارات المتصفح والجوال.
4. نشر حزمة Linux واختبار التطبيق المنشور، ثم بناء Windows x64 ذاتية الاحتواء لـIIS.
5. فحص payload ورفع artifact باسم `publish`، باحتفاظ **7 أيام** حاليًا.
6. على push/main فقط: prepare ثم رفع FTPS ثم finish ثم health ثم تدقيق الملفات والأصول وحفظ الدليل.

لبناء حزمة دون نشر:

```bash
dotnet publish Payroll.Api/Payroll.Api.csproj -c Release -r win-x64 --self-contained true -o artifacts/monsterasp --nologo
python3 scripts/check_publish.py artifacts/monsterasp
```

الموقع IIS يعمل بمعمارية x64 المتوافقة مع الحزمة. وجود Node محلي لا يعني احتياجه كخادم إنتاج. الأوامر المحلية التاريخية في [DEPLOYMENT_AR](../../DEPLOYMENT_AR.md) قد تحمل عنوان إصدار أقدم؛ workflow وكود التحقق هما مرجع السلوك الحالي.

## دورة نشر MonsterASP عبر FTPS

إعداد الاتصال يُحقن خصوصيًا في بيئة التشغيل المعتمدة. لا تضع أي قيم اتصال أو حساب أو كلمة مرور في التوثيق أو الأوامر أو السجل. FTPS يستخدم TLS مع تحقق الشهادة واسم الخادم؛ استكمال intermediate ناقص يتم بسلسلة موثقة وجذور النظام، دون تعطيل التحقق.

1. تأكد من موافقة النشر والرأس المختبر ووجود artifact سابق صالح خارج مدة انتهاء GitHub، ونسخة خاصة قابلة للاستعادة. لا تبنِ الحزمة من قاعدة تطوير ولا تضف بيانات تشغيل.
2. `scripts/monsterasp_ftps.py check` يفحص الاتصال والموقع قراءة فقط. إخفاقه يمنع الرفع.
3. `prepare` يرفض علامة صيانة لمشغل آخر، ويكتب `app_offline.htm` خاصة بالتشغيل ويترك IIS يوقف التطبيق، ثم يسجل بصمة metadata للبيانات المحمية. لو فشل قبل نقل الملفات يحاول استعادة حالة علامة الصيانة السابقة.
4. خطوة FTPS ترفع حزمة التطبيق النظيفة. `dangerous-clean-slate: false`؛ `App_Data` والإعداد المحلي وعلامة الصيانة مستبعدة. لا ترفع مجلد المشروع كله ولا تنظف جذر الموقع.
5. `finish` يفحص ملكية العلامة وتطابق metadata المحمية، ثم يزيل العلامة. اختلافها يبقي الصيانة للفحص؛ لا تحذف العلامة يدويًا لإجبار الإقلاع.
6. عند بدء الإصدار، `ReleaseSafety` ينشئ checkpoint إن احتاجه ويتحقق من حفظ الوثائق قبل/بعد إعداد الفهارس. فشله يمنع بدء الإصدار بنجاح.
7. شغّل health وتحقق payload؛ نجاح نقل الملفات وحده لا يكفي لإعلان نجاح النشر.

لا يوجد تعافٍ تلقائي يعيد الإصدار السابق إذا فشل الرفع أو التدقيق بعده. قد تكون الملفات الجديدة حية رغم فشل آخر خطوة CI؛ افحص المرحلة التي فشلت قبل اتخاذ إجراء.

## Health وتدقيق الإصدار

الفحص العام قراءة فقط:

```bash
curl --fail --silent --show-error https://payroll.marketingalbawaba.com/health
python3 scripts/monsterasp_ftps.py health
```

معايير الإصدار الحالي: `ok=true`، و`version=0.7.0`، و`dataPreservationVerified=true`، و`releaseCheckpointPresent=true`. الإصدار المتوقع مثبت حاليًا في أداة health؛ حدثه مع الإصدار القادم، ولا تعتبر فشل شرط الإصدار وحده دليل فقد بيانات.

`verify_deployed_payload.py` يطابق SHA256 لكل ملف منشور على الخادم، ويفحص أصول HTTPS الأصلية وبصماتها. ملفات `.br/.gz` الجانبية تبقى ضمن فحص الملفات؛ لا يلزم رابط HTTPS مستقل للضغط الجانبي حين يوجد أصله. غياب ملف أصلي أو اختلاف بصمته فشل حقيقي، ولا يُستثنى كملف ضغط.

التدقيق يقرأ metadata للـcheckpoint فقط، ولا ينزل قاعدة الإنتاج أو المفاتيح. دليل التحقق الجزئي يُحفظ حتى عند فشل الأداة، وartifact دليل النشر يحتفظ به **14 يومًا**. `/api/system/release-check` للمسؤول ويحتوي تفاصيل خاصة؛ لا تنسخ مخرجاته إلى docs.

نجاح هذه الفحوص يثبت الإصدار وحفظ البيانات؛ اعتماد الأرصدة القديمة يحتاج مستندات ومطابقة مالية منفصلة.

## Rollback — التراجع

مسار إجرائي للمشغل المعتمد؛ لا توجد workflow جاهزة بزر واحد حتى الآن.

1. أوقف عمليات مالية جديدة وامنع تداخل نشرين. حدد هل الخلل في التطبيق أم البيانات، وهل الموقع في الصيانة أم حَي بعد فشل التدقيق.
2. اختر **الحزمة السابقة المختبرة نفسها** وتحقق من بصمتها وتوافق كودها مع البيانات الحالية. لا تستخدم ملف source zip كحزمة تشغيل ولا تعِد البناء من فرع قد تغير.
3. بعد موافقة Ghazal، استخدم دورة prepare → رفع حزمة التطبيق السابقة فقط → finish، مع نفس استبعادات البيانات والإعدادات. احتفظ بحالة prepare الخاصة بهذه الدورة، ولا تتجاوز رفض ملكية العلامة أو تغير metadata.
4. افحص `/health` للإصدار السابق المقصود، ثم تدقيق ملفاته وأصوله. مدقق الإصدار الحالي يتوقع `0.7.0`؛ عند الرجوع لإصدار آخر استخدم مدققًا متوافقًا مع تلك الحزمة أو مراجعة صريحة للنسخة المتوقعة، دون إضعاف التحقق من الحفظ والبصمات.
5. تحقق من الدخول والروابط العامة والكشوف قراءة فقط، ثم راجع المالية قبل استئناف العمليات. دوّن الحزمة والرأس وسبب التراجع والنتيجة في HANDOFF.

التراجع بالكود لا يعكس قيودًا مالية ولا يستعيد تلقائيًا قاعدة البيانات. استعادة checkpoint قد تفقد حركات تمت بعده؛ تحتاج قرارًا صريحًا وتحديدًا لهذه الحركات، وإيقاف التطبيق وحفظ الحالة الحالية أولًا. لا تستعد قاعدة فوق قاعدة جارية.

## Backups — النسخ والاستعادة

المتوفر حاليًا:

- `ReleaseSafety` يحفظ checkpoint خاصًا لكل إصدار: SQLite عبر Backup API وفحص integrity، أو snapshot منطقي لوثائق SQL Server بمعاملة Serializable؛ مع manifest ومفاتيح الجلسات والإعداد المحلي إن وجدت. النسخة على **نفس السيرفر**، ولا يوجد تدوير أو جدولة خارجية مثبتة.
- `scripts/backup_data.py` أداة SQLite: نسخة متسقة مع `integrity_check` ومفاتيح الجلسات في ZIP خاص بصلاحيات مقيدة. لا يشفّر ZIP، ولا ينسخ المرفقات أو الإعداد المحلي؛ يجب إدراجهما في خطة النسخ الكاملة على حدة.

صيغة التشغيل التالية تستخدم مسارات placeholder يحددها المشغل خصوصيًا، ولا تُشغّل ضمن مهمة التوثيق:

```bash
python3 scripts/backup_data.py --data-dir PRIVATE-DATA-DIRECTORY --output-dir PRIVATE-BACKUP-DIRECTORY
```

لا تنسخ ملف SQLite الرئيسي وحده أثناء الكتابة؛ WAL قد يحتوي تغييرات غير مدمجة. استخدم Backup API أو خدمة نسخ متسقة من الاستضافة. لا تحفظ ZIP تحت الأصول العامة أو داخل Git/artifacts المشتركة.

خطة الاستعادة: اختبر النسخة في وجهة خاصة ومعزولة، وافحص سلامة القاعدة وأعداد الوثائق وبصمتها والمفاتيح والإعدادات والمرفقات المطلوبة. طابق ميزان الحسابات والذمم والجاري والدفتر القديم، مع تعطيل الإرسال الخارجي. لا تستبدل الإنتاج إلا بإذن وإيقاف كتابة ونسخة من الحالة الحالية وخطة معالجة ما بعد تاريخ النسخة.

SQL Server snapshot الخاص بالإصدار منطقي وليس ملف `.bak` كاملًا للخادم. أداة `StoreMigration` تدعم export/preview/import إلى **وجهة فارغة** ببصمة مراجعة؛ ليست أداة overwrite أو تراجع تلقائي. استعادة SQL Server تحتاج إجراءً خاصًا مختبرًا ومفاتيح التطبيق والمرفقات، لا معاملة snapshot كنشر تطبيق.

المطلوب: نسخة يومية مشفرة خارج الاستضافة، واحتفاظ مقترح يومي 14 وشهري 12، واختبار استعادة شهري، وحفظ آخر حزمة صالحة أطول من سبعة أيام. هذه توصيات S2 وليست خدمة مفعلة حاليًا.
