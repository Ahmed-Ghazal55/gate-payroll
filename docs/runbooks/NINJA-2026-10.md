# نينجا — أول دورة رواتب، أكتوبر 2026

الحالة: مسار Backend متحقق ببيانات مصطنعة على SQL Server عبر HTTP. تنفيذ الواجهة على البيانات الحقيقية **لم يُتحقق منه** في هذه الجلسة. يلزم دمج واجهة Antigravity ومراجعة Claude، ثم موافقة غزال على أي نشر. C6 وC7 عند Claude.

الشاشة الحالية «فتح شاشة رفع ومطابقة فاتورة نينجا» تنفذ المطابقة فقط. خطوات التأكيد والاعتماد التالية تصف واجهة R8 المطلوب دمجها؛ ليست نقرات مثبتة على النسخة المنشورة الحالية. عقد lookup ينتظر C6؛ بعد دمج C6/C7 يعاد توليد OpenAPI والأنواع وفحص ردودهما.

## قبل البداية

- القاعدة المطلوبة `db77738`، وقاعدة ERP `db67927` للقراءة فقط. لا تغيّر الاتصال أو تقرأ ملفات الأسرار. مسؤول التشغيل يؤكد قاعدة الموقع قبل تجربة البيانات الحقيقية؛ `/health` وحده لا يثبت اسم القاعدة.
- اختَر الشركة والشهر `2026-10` والمنصة Ninja. لا تجمع شركات مختلفة في دورة.
- حساب المُجهّز معه `pay.manage` وحساب مستقل معه `pay.approve`. المعتمد النهائي لم يُجهّز أي مرحلة من الدورة.
- كل **كتابة حقيقية** أدناه لها تصريح «حمّل» مستقل، يشمل اسم الخطوة والشركة والشهر. الدخول في هذا الدليل أو إجراء GET ليس تصريح كتابة.
- لا تشارك صورًا أو ملفات أو JSON فيها بيانات مناديب. سجل المعاينة يحوي أعدادًا وإجماليات فقط، وصلاحيته `600` خارج Git.

## 1. الإعدادات — معاينة أولًا

من «الرواتب» ← إعدادات Ninja ← أكتوبر 2026، راجع الشروط الأصلية، والأهلية، وكل نظام سيُطبّق، وإعدادات الأيام والإيجار بتاريخ أول الشهر. النسخ المطلوبة حالتها `approved`؛ قيم العقد لا تُعتمد من قالب المحرك تلقائيًا.

القراءة المقابلة في API:

```text
GET /api/pay/apps/ninja/terms?period=2026-10
GET /api/pay/apps/ninja/eligibility?period=2026-10
GET /api/pay/apps/ninja/schemes?period=2026-10
GET /api/pay/settings
GET /api/pay/apps/ninja/assignments?period=2026-10
GET /api/pay/catalog
```

- افتح شروط الأهلية: `metric` من `ninjaMetrics`، ومعه `operator`, `threshold`, `effect.type`, `included`. غياب `included` في نسخة قديمة يعني شرطًا فعالًا. شرط مستبعد لا يطبّق ولا يطلب مقياسًا مفقودًا.
- اختيار نظام المندوب معتمد **قبل بداية الشهر**. غياب الاختيار يوقف المسودة؛ لا تستنتج النظام من اسم المندوب أو مالك الحساب.
- لو احتجت تصحيحًا: **توقف لتصريح كتابة** لإنشاء المسودة، ثم تصريح مستقل لاعتمادها من الشخص الآخر. النسخة المعتمدة لا تتعدل.
- رفض مسودة يحتاج سببًا. الحذف لمسودة فقط، بواسطة صاحبها أو الأدمن؛ مسودة أهلية مرتبطة بنظام لا تُحذف قبل فك مسودة النظام.

## 2. فاتورة المنصة

من «استيراد البيانات» ← «فاتورة نينجا»، اختر الشركة والشهر ومرجعًا للملف، ثم ارفع ملف المنصة الأصلي 43 عمودًا للمعاينة. لا تعدّل قيم الفاتورة لتوافق المتوقع.

```text
POST /api/platforms/ninja/invoices                  multipart: file, companyId, period, reference
POST /api/platforms/ninja/invoices?commit=1         نفس الملف + rows, fingerprint, confirm=true
GET  /api/platforms/ninja/invoices
GET  /api/platforms/ninja/invoices/{id}
GET  /api/platforms/ninja/invoices/{id}/lines
```

- المعاينة `canCommit=true`، والفاتورة داخل `rows[0]` تعرض `approvalStatus=pending`, `allowedActions=[confirm]`.
- لملف حساب واحد أو عدة حسابات: مرر الحقل المتكرر `accountIds[]`، أو قائمة JSON في `accountIds`. أي `captain_id` خارج الاختيار يرفض الملف ويعرض **أرقام الصفوف** فقط.
- الملف المجمع يعمل بدون `accountIds`.
- القرار: **فاتورة لكل ملف**؛ فواتير الحسابات المختلفة لنفس الشركة والشهر تدخل معًا في دورة واحدة. نفس بصمة الملف تعيد نفس الفاتورة بلا إضافة. الحساب الموجود في ملف آخر لنفس الشهر يُرفض لمنع تكرار الاستحقاق.
- راجع `baseGross + incentives - deductionAmount = invoiced` لكل سطر، و`invoiced + vat = totalCost` في الملف.
- فروق `expected` مقابل `invoiced` للمراجعة فقط (§31)، وليست اعتراضًا تلقائيًا ولا مانع ترحيل.
- **توقف لتصريح «حمّل تأكيد فاتورة نينجا»** قبل زر التأكيد.

## 3. التصنيف والاعتماد والاعتراض

من تفاصيل الفاتورة، صنّف كل خصم على الشركة أو الحساب. خصم الشركة يحتاج حساب تكلفة فعالًا. لا تحمّل خصم الشركة على المندوب.

```text
POST /api/platforms/ninja/invoices/{id}/classify    lineId, category, level, expenseAccount عند الحاجة
POST /api/platforms/ninja/invoices/{id}/approve
POST /api/platforms/ninja/invoices/{id}/dispute     reason
POST /api/platforms/ninja/invoices/{id}/resolve     disputeId, reason
```

كل إجراء كتابة يحتاج تصريحه. المعتمد مستقل عن رافع الفاتورة ومصنّفي خصوماتها. بعد الاعتماد: `approvalStatus=approved`, `status=final`. اقرأ الأزرار من `allowedActions` بعد كل استجابة؛ لا تستنتجها في UI.

لو يوجد اعتراض رسمي حقيقي، سجله واحسمه من شخص مستقل قبل الدورة. **لا تستخدم `.../post` المنفصل لهذه الدورة**؛ اعتماد المرحلة 7 يرحّل الفاتورة والرواتب في قيد الدورة، ويمنع تكرار الإيراد. الترحيل المنفصل موجود لمسار الفواتير المستقل فقط.

## 4. التشغيل ومدخل المراجعة

من «استيراد البيانات» ← «تشغيل نينجا»، نزّل القالب، وحدد الفاتورة المعتمدة. راجع حساب المنصة، المشغل الفعلي، الطلبات، الأيام، فئة الكفالة والمركبة، الاستحقاق الأساسي، توزيع خصم الحساب، ومقاييس الأهلية.

```text
GET  /api/imports/templates/operations-ninja
POST /api/pay/apps/ninja/operations/import/preview  invoiceId, dataBase64
POST /api/pay/apps/ninja/operations/import/commit   نفس المدخل + rows, fingerprint, confirm=true
GET  /api/pay/review-draft?app=ninja&period=2026-10&companyId=<الشركة المختارة>
```

المعاينة لا ترحّل رواتب أو تنشئ دينًا. تأكيد التشغيل يحتاج «حمّل» مستقلة. آخر مراجعة تشغيل محفوظة للفاتورة هي المدخل المقترح؛ تُعاد مطابقتها بالمصدر عند القراءة.

لو توجد بيانات `ninja_daily` كاملة، يمكن اقتراح حساب ذي مشغل واحد وفئة مراجعة صريحة. الحساب متعدد المشغلين يحتاج توزيع D3 مراجع؛ لا تقسيم افتراضي للاستحقاق أو الخصم. الحوافز فقط تُوزع بنسبة الطلبات داخل المحرك.

النجاح: `canCreate=true`, `blockers=[]`. راجع `unassignedOrders`, `ridersNotFound`, `evidence`. كل حساب ومندوب يحمل `sourceLineId`؛ مراجع التشغيل تنتقل لسطور الدورة والكشف.

أسباب توقف محتملة، وليست نتائج مثبتة على البيانات الحقيقية:

| code | الإصلاح |
|---|---|
| invoice_missing / invoice_not_approved | رفع/اعتماد الفاتورة |
| pay_terms_missing / pay_eligibility_missing / global_settings_missing | اعتماد نسخة إعداد مناسبة |
| operations_missing / allocation_required / category_missing | استيراد توزيع التشغيل المراجع |
| unassigned_orders / rider_not_found | مراجعة تكليف الحساب أو مزامنة المندوب |
| orders_mismatch / operations_review_invalid | تصحيح توزيع التشغيل ليتطابق مع الفاتورة |
| scheme_assignment_missing / metric_missing | اختيار نظام معتمد قبل الشهر أو استكمال مقياس موثق |
| open_dispute / invoice_already_posted / cycle_exists | استكمال المسار الموجود قبل بدء دورة جديدة |

## 5. الدورة والمراجعة والكشف والقيد

بعد «حمّل إنشاء دورة نينجا»، واجهة الرواتب ترسل `period, companyId, app=ninja, invoices` من مسودة المراجعة. لا ترسل `blockers`, `totals`, `evidence` داخل مدخل الإنشاء.

```text
POST /api/pay/cycles
POST /api/pay/cycles/{id}/capture-inputs            زر «التقاط المدخلات» (0.21.0، BR §39.2)؛ مسموح حتى المرحلة 1 فقط
POST /api/pay/cycles/{id}/advance                   stage=1 ثم 2 ثم 3 ثم 4 ثم 5 ثم 6
GET  /api/pay/cycles/{id}/lines
GET  /api/pay/cycles/{id}/review
POST /api/pay/cycles/{id}/review/{iqama}             action=approve أو edit/adjust بسبب
POST /api/pay/cycles/{id}/review/approve-all
POST /api/pay/cycles/{id}/advance                   stage=7، بواسطة المعتمد المستقل
GET  /api/finance/statement/rider/{iqama}/monthly?period=2026-10
```

من 0.21.0: التقط المدخلات قبل الانتقال للمرحلة 2، وراجع عدد الصفوف لكل نوع في بطاقة المدخلات (لا صفر في الأداء اليومي وحسابات المنصة وتسليم المركبات). بعد المرحلة 1 لا التقاط جديد: أي تغيير في نظام الموارد = ألغِ الدورة وأنشئ أخرى (قاعدة «أ٠»). كل انتقال/تعديل/اعتماد كتابة مستقلة تحتاج تصريحها. في المرحلة 6 راجع كل الصفوف من الجدول الواحد: الإجمالي، العمولة، المستحق الأولي، مراحل الاستقطاع، الصافي. «اعتماد الكل» لا يعتمد الصفوف التي تحتاج قرارًا. لا تنتقل للمرحلة 7 قبل اعتماد كل الصفوف.

بعد تصريح الاعتماد النهائي وحساب الشخص الآخر:

- الدورة `approved` ومعها `journalEntryId`؛ الفاتورة تشير لنفس القيد و`accountingStatus=posted`.
- افتح كشف كل مندوب من نفس الشاشة. `status=approved`، وكل بند مصدره موجود في `cards[].sources` وشرح المعادلة في `cards[].explain`.
- من «المحاسبة» ← «القيود»، افتح قيد الدورة: المدين يساوي الدائن، ذمة Ninja `112806`، الإيراد `411104`، VAT `213201`، ومستحق المناديب `212103`.
- إعادة اعتماد المرحلة 7 بنفس المعتمد تعيد نفس القيد. إعادة إنشاء دورة موجودة مرفوضة؛ لا فاتورة ولا قيد جديد من الإعادة.

## 6. المقارنة مع Excel

قارن محليًا، من غير نقل بيانات شخصية للريبو أو السجل المشترك:

1. لكل حساب: الطلبات، الأساسي، الحوافز، كل خصم مصنف، المفوتر، والضريبة. المقترح يطابق الفاتورة قبل الضريبة والخصومات.
2. لكل مندوب: نصيبه من طلبات الحساب والأساسي، نصيب الحوافز بنسبة الطلبات، النظام وفئته، أيامه، العمولة، المراحل 1/2/3، والصافي.
3. لا تخصم VAT من المندوب؛ الضريبة خارج استحقاقه. خصم الشركة لا ينقص صافي المندوب؛ يظل تكلفة شركة.
4. اجمع ذمة المنصة في القيد: إجمالي الفواتير الأساسي والحوافز + الضريبة - خصومات الحسابات والشركة. قارنها بصافي فاتورة المنصة شامل الضريبة.
5. قارن مجموع كشف المناديب بمجموع مستحقاتهم في الدورة. فروق الأنظمة الداخلية والعمولات وتكلفة الشركة واضحة كبنود مستقلة؛ لا تتوقع مساواة صافي المناديب بصافي فاتورة المنصة دائمًا.
6. الأقساط تخصم مرة واحدة وبحد القسط المستحق، والدين المرحل لا يخصم كله مجددًا.

## 7. التصحيح بالعكس

لا تعديل أو حذف لقيد معتمد. بعد تصريح طلب العكس، اكتب سببًا وشهرًا مفتوحًا، ثم تصريح مستقل لاعتماد العكس بشخص آخر:

```text
POST /api/pay/cycles/{id}/advance    action=reversal_request, period, note
POST /api/pay/cycles/{id}/advance    action=reversal_approve
```

الأصل يظل محفوظًا، ويضاف قيد عكسي. الدورة والفاتورة تعرضان العكس، والكشف يستبعد الدورة المعكوسة. الصرف اللاحق أو حركة الدين اللاحقة تمنع العكس حتى تسويتها. دورة التصحيح تحتاج فاتورة مصححة و`replacesCycleId` صريحًا؛ لا تعيد الفاتورة القديمة لتكرار الإيراد.

## معاينة حقيقية للقراءة فقط من المتصفح

بعد دمج R8 وتشغيله على الموقع الصحيح، سجّل دخولك، ثم DevTools ← Console. الأمر التالي يستخدم جلستك الحالية؛ لا تنسخ Cookie ولا كلمة مرور. كل الطلبات GET. الناتج أعداد وإجماليات ورسائل عوائق عامة فقط؛ لا أسماء أو هويات أو مبالغ فردية:

```javascript
const get = async path => {
  const r = await fetch(path, { credentials: 'same-origin' });
  if (!r.ok) throw new Error(`GET failed: ${r.status}`);
  return r.json();
};
const companies = await get('/api/companies');
const report = { status: 'read_only', period: '2026-10', app: 'ninja',
  checkedAt: new Date().toISOString(), databaseConfirmedByOperator: 'db77738', companies: [] };
for (const company of companies.filter(c => ['BW', 'EX', 'TR'].includes(c.code))) {
  const d = await get(`/api/pay/review-draft?app=ninja&period=2026-10&companyId=${encodeURIComponent(company.id)}`);
  report.companies.push({ code: company.code, canCreate: d.canCreate,
    invoices: d.invoices.length,
    accounts: d.invoices.reduce((n, i) => n + i.accounts.length, 0),
    riderShares: d.invoices.reduce((n, i) => n + i.accounts.reduce((m, a) => m + a.riders.length, 0), 0),
    unassignedRows: d.unassignedOrders.length, missingRiderRows: d.ridersNotFound.length,
    blockerCounts: Object.fromEntries([...new Set(d.blockers.map(b => b.code))]
      .map(code => [code, d.blockers.filter(b => b.code === code).length])),
    totals: d.totals });
}
const link = document.createElement('a');
const url = URL.createObjectURL(new Blob([JSON.stringify(report, null, 2)], {type: 'application/json'}));
link.href = url; link.download = 'r8-ninja-dryrun.json'; link.click(); URL.revokeObjectURL(url);
console.log('Read-only report downloaded; no payroll writes.');
```

لو ظهر 404، نسخة R8 غير متاحة على هذا الموقع؛ توقف. لا تغيّر القاعدة ولا تشغّل نسخة API عادية مباشرة على القاعدة الحقيقية للمعاينة، لأن بدء التطبيق نفسه يحتوي seed/migration writes.

بعد التنزيل، شغّل في Terminal:

```bash
install -m 600 "$HOME/Downloads/r8-ninja-dryrun.json" "$HOME/Private/gate-data/sync-logs/r8-ninja-dryrun.json"
```

نتيجة هذه الجلسة: لم تتوفر جلسة متصفح حقيقية مصرح بها؛ لم تُقرأ ملفات `~/Private`، ولم تُنفذ معاينة حقيقية أو كتابة على `db77738`. ملف حالة `not_run` لا يثبت أي أعداد أو عوائق حقيقية.
