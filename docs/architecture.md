# Architecture — بنية التطبيق

مطابق للكود وS1–S7 في [فهرس المصادر](README.md)، بتاريخ 2026-10-26.

## حدود النظام

تطبيق ASP.NET Core Minimal API على `.NET 10`، وواجهات TypeScript وCSS، تحت أصل HTTPS واحد على Windows/IIS في MonsterASP. Node.js أداة بناء واختبار. لا يوجد React أو Next.js أو NestJS في هذا المشروع.

ثلاث شركات مستقلة محاسبيًا: `BW` البوابة المقبلة للتجارة، `EX` إكسبرس جايت، `TR` مؤسسة البوابة المقبلة التجارية. `sponsorId` على السطر المالي يحدد الشركة؛ الكفالة وحدها لا تحدد مالك الراتب أو الدين. البنوك مستقلة، والدفع بالنيابة يحتاج دليلًا وجاريًا صريحًا.

سياسة الشركة والبوستر، حساب الرواتب، والنماذج مجالات منفصلة. البوستر ليس مصدر استحقاق فعلي. اختيار نظام العمل في الفورم لا يعين `policyId`. ERP الرئيسي مشروع منفصل؛ لا يوجد تكامل يضمن تلقائيًا أن دفتره ودفتر Payroll متطابقان. تحديد دفتر المرجع ما زال قرارًا مفتوحًا.

## التخزين والمعاملات

[Store.cs](../Payroll.Api/Store.cs) يخزن الوثائق في جدول واحد `records(id, kind, body)`؛ `body` JSON. أنواع الوثائق تشمل `rider` و`work` و`run` و`ledger` و`payment` و`debt` و`journal` و`debt_transfer` و`opening_reconciliation` و`submission` و`audit`. هذه أنواع داخل جدول، وليست جداول علائقية مستقلة.

SQLite هو الافتراضي والمذكور كتشغيل إنتاج في S2؛ SQL Server مزود بديل موجود ومختبر في CI. لا يوجد مزود PostgreSQL منفذ. لا يغير إصدار جديد المزود أو يستبدل قاعدة التشغيل تلقائيًا.

SQLite يستخدم WAL، وفهارس على الأنواع وبعض حقول JSON، وفهارس تفرد للمسير حسب الفترة/الشخص ولرد الحملة وللمستخدم. SQL Server لديه حاليًا فهرس `kind` دون كل نظائر فهارس SQLite. الكتابة داخل `Serializable transaction`، أي معاملة تمنع تعارض الكتابات، مع قفل داخل العملية؛ SQL Server يضيف `sp_getapplock`. وثيقة العمل وقيدها وسجلها تُحفظ في المعاملة نفسها.

`Store.List` يحمل كل وثائق النوع. حساب الأرصدة والمعاينات المالية يمسح مجموعات كبيرة؛ لا توجد بعد projection لسطور القيود أو خدمة أرصدة مفهرسة. بصمة الاستيراد المالي تتأثر حاليًا ببيانات واسعة، ولذلك قد تبطل معاينة بسبب حركة غير مرتبطة بها.

بيانات التشغيل والمرفقات ومفاتيح الجلسات تبقى في مجلد خاص خارج الأصول العامة. `App_Data` والإعداد المحلي مستبعدان من publish. `ReleaseSafety` يأخذ checkpoint قبل التحديث الإضافي للفهارس ويتحقق من أعداد الوثائق وبصمتها؛ ذلك يثبت الحفظ ولا يعتمد صحة رصيد تاريخي.

## حساب الرواتب

المصدر المالي الفعلي يحدد استحقاق المنصة، وسياسة الشركة تحدد راتب المندوب. تربط أسطر العمل بالشخص الفعلي وفترات استخدام حساب المنصة، وتبقى معرفات الحسابات نصوصًا. العمولة الشهرية مرة للشخص/الفترة، ولا تستنتج حوافز ترتيب المنصة من حدود طلبات البوستر.

اعتماد المسير يحتاج fingerprint، أي بصمة تثبت أن البيانات لم تتغير بعد المعاينة. المسير المعتمد لا يعدّل مباشرة. الأستاذ القديم `ledger` وقيود `2110/1211` يجب أن يتطابقا قبل الاعتماد، والمدفوع المسجل لنفس الفترة لا يرحل ثانية. التفصيل في [Posting rules](accounting/posting-rules.md).

## بناء الواجهات

```bash
npm ci --no-audit --no-fund --prefix RiderForm
npm run build:all --prefix RiderForm
dotnet build tests/Engine.Tests -v q
```

TypeScript الفعلي مثبت على `5.9.3` في `RiderForm/package.json` والقفل؛ ذكر TS7 في سياق أقدم تجاوزه التصحيح. `RiderForm/src/rider-form.ts` بوضع strict، والإدارة في `Frontend/src` بوضع تدريجي (`strict: false`). `noEmitOnError` مفعل في الاثنين.

المخرجات تُكتب إلى `Payroll.Api/wwwroot`. هدف `BuildChoiceFrontend` في csproj يشغل `build:all` وينسخ `RiderForm/web/rider-form.html`، لذلك `dotnet build/publish` يبني الواجهتين أيضًا. لا تعدل ملفات JS المولدة.

الإدارة تحمل scripts بهذا الترتيب مع `defer`: `app.js` ثم `table-tools.js` ثم `enterprise.js` ثم `bootstrap.js`. البنية تعتمد globals وtemplate strings و`innerHTML`؛ ليست bundler أو SPA framework. الحفاظ على escaping وترتيب التحميل ضروري.

نموذج اختيار العمل الافتراضي ثلاثة حقول: هوية نصية، اسم، واختيار واحد بلا قيمة افتراضية. التحقق على العميل والخادم، والأرقام ASCII، ومنع التكرار داخل الحملة. تبقى النماذج الديناميكية مسارًا منفصلًا؛ لا توسع نموذج الاختيار الأصلي ضمنيًا.

## Mobile والمصادقة

`/inquiry` للاستعلام و`/rider-app` لبوابة المندوب تحت نفس التطبيق. HTML وJS لبوابة mobile مضمنان حاليًا كنصوص في `FinancialCore.cs`. الدخول يحتاج رمز وصول خاصًا صادرًا بعد مراجعة الهوية وبنطاق مناسب، مع تحقق بيانات مسجلة؛ معرفة الهوية وحدها لا تكفي. جلسة mobile محدودة المدة، ورمزها محفوظ كبصمة على الخادم.

الإشعارات الحالية `in_app`: مخزنة وتظهر عند فتح البوابة مع إقرار قراءة عند طلبه. حفظ إعدادات Firebase ليس إرسال FCM فعليًا، ولا يوجد نشر Google Play مكتمل. OTP عبر Telegram أو WhatsApp في المخطط الأول اقتراحات لم تُنفذ، ولا يوجد ضمان انعدام التكلفة أو الأعطال.

فصل أصول mobile إلى ملفات مستقلة، كشف PDF والاعتراضات، الإرسال الخارجي والتطبيق المنشور أعمال لاحقة في [Roadmap](roadmap.md).
