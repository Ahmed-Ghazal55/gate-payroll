# R4 pay framework

This is an additive path beside the legacy engine. Engine.cs, historical payroll runs and existing journal bodies are unchanged. No actual app rates/bands are invented; all values come from approved versioned records. Jahez remains a separate settlement cycle (BR24.9).

## Versioned settings

`GET /api/pay/catalog` exposes app/account metadata, scheme types, six category keys, operators and an **unapproved** global-default template. `pay.view`, `pay.manage`, `pay.approve` are separate permissions. Existing users receive current role defaults on cookie validation without rewriting their documents. Shared settings writes/approvals additionally require all-company scope and the app platform scope; a FIN checker differs from the preparer, even for administrators.

| Routes | Contract |
|---|---|
| GET/POST `/api/pay/apps/{app}/terms?period=` | Parent billing: per_order, slabs, flat_target; typed model parameters |
| GET/POST `/api/pay/apps/{app}/schemes?period=` | Named internal schemes; explicit accountingRole=principal/agent and six category cells |
| GET/POST `/api/pay/apps/{app}/eligibility?period=` | Rules owned by exactly one app/month |
| POST `…/terms|schemes|eligibility/{id}/approve` | Independently approve latest draft only |
| POST `/api/pay/apps/{app}/copy?from=&to=` | Copy approved prior-month configurations to drafts; preserve linked eligibility snapshots |
| GET/POST `/api/pay/settings` | Global effective-dated version history / new draft |
| POST `/api/pay/settings/{id}/approve` | Independent global approval |

GET lists always return items/total/page/pageSize (max200). App POST body: `{period,code?,data,baseVersionId?}`. A supplied query period must match the body. Terms/eligibility default to code=default; schemes require a code. Every POST appends a new draft; accepted approval metadata is server-owned. Repeating approval is unchanged. An approved version is immutable, and existing cycles will reference exact version IDs. Copy is idempotent for matching drafts, never overwrites approved target versions, and forks an older referenced eligibility snapshot under its own code when necessary. Copied rule references must be approved before their scheme.

`data` for terms: name, billingModel, parameters. Per order requires pricePerOrder; optional distance pricing requires perKmRate/includedKm/maxBillableKm together. Slabs require metric and bands. Flat target requires targetOrders/monthlyAmount/extraRate/shortfallPerOrder/prorate. A configured companyCostAccount must be an active expense account.

Scheme data: name/type/accountingRole/parameters and optional eligibilitySetId. `parameters.categories` explicitly contains sponsored_company_car, sponsored_company_bike, sponsored_private, external_company_car, external_company_bike, external_private. Each cell is `{enabled:false}` or has chargeCompanyVehicle and its formula values: dailyCommission; companyPercent; monthlyCommission plus prorate; or target_salary bands. percent_monthly_with_vehicle explicitly charges a company vehicle. Bands have min, optional max, base/perOrderRate, optional extraRate/fuelCap/internet and optional multiplierMetric/multiplierDivisor. Missing cells/rates or another app/month's eligibility reference are refused.

Eligibility data: name/rules; each rule has metric/operator/threshold/effect. Operators: gt/gte/eq/neq/lt/lte. Effects: `{type:next_band|per_order|zero}`. No shared app rule sets; referenced versions remain exact snapshots.

Global POST body: `{effectiveFrom,fromDefaults:true}` or `{effectiveFrom,data:{values:…}}`. Values include standardDays/februaryDays/billingCutoff/timeZone/roundingDigits/roundingMode/vehicleRent/accounts. The embedded defaults are configuration data (30/28 days,14:00 Riyadh,1800/800 company rents,2dp AwayFromZero), never auto-approved. No rates live in evaluator branches. Ghazal confirmed that billed assignment days are capped at30/28, including31-day/leap-February months.

R4 keeps source data unchanged during previews. Ghazal clarified that actual approved debt installments use existing Debts.Post and update the balance at approval only; this is an authorized business transaction, not a startup migration.

## Approved rider choices (R4.3)
GET `/api/pay/apps/{app}/assignments?period=` returns scoped approved-choice history. POST `/assignments/import/preview|commit` under the same app path is administrator-only: `{period,sourceType:campaign|custom,formId,fieldId,mapping:{choice:approvedSchemeId}}`. Campaign choice field is workSystem; custom forms require a select/radio field and an iqama identity field. When a custom form has several identities, explicitly supply riderFieldId for the actual operator; the owner is never a substitute.

Preview reads current responses and archived approved history, then selects the latest approved choice strictly before Riyadh00:00 on the month's first day. Unapproved/late rows are counted separately; missing approval evidence, an unmapped latest choice or conflicting simultaneous choices block the batch instead of falling back to an older choice. The mapped scheme must already be approved for the exact app and period. Source reviewedAt/approvedAt and reviewer are required; createdAt is not a substitute.

Confirm with period and the returned rows/fingerprint/confirm. The signature binds the actor, current source responses/forms/riders/settings and imported choices. Repeated imports are unchanged. A newly approved source-response version creates another immutable choice; it never rewrites an earlier choice, response, rider or legacy policy. Company visibility uses the assignment's historical company snapshot, not a later rider transfer. Effective resolution uses the latest imported pre-month approval across mapped source forms and rejects equal-time conflicting schemes. No assignment is inferred from an account owner's identity.

## Pure evaluator
`PayEvaluator` reads approved setting snapshots. Billed days are capped at configured30/28, including31-day/leap-February months. Pickup/return use strict after14:00 Riyadh boundaries. Incentives use actual order shares with deterministic largest-remainder cents. No account owner fallback. Fuel caps are informational, not cash allowances. Missing metrics/vehicle evidence and negative net return `needs_decision`; no debt is created. Explain lines show formula, inputs and amount. Fallback operating costs require an explicit active target income account.

## Monthly cycles
`POST /api/pay/cycles` takes `period`, `companyId`, optional `app`, `invoices` and `adjustmentAccounts` (source adjustment id → explicit target account). One active cycle per company/month merges apps; Jahez is refused. Each invoice references an independently approved, unposted `platform_invoice` of the same company/app/period. Review contains `accounts` (`accountId`, `sourceLineId`, `baseGross`, `incentives`, `orders`, `riders`) and `deductions` (`sourceLineId`, `level:company_level|account_level`, `amount`, optional `accountId`, company `expenseAccount`). Gross and classified deductions must match source `amountExclVat` and `deductionsTotal`; VAT comes from source. Account source lines must carry the same platform-account id. An importer/source that lacks this evidence must be normalized/reviewed before cycle creation; this endpoint does not import arbitrary invoice files.
Each rider share supplies actual `rider`, `orders`, `baseGross`, explicit `deduction`, reviewed six-cell `category`, app-wide actual `days` and `metrics`. ERP account assignments must prove actual operation during the month, with RawEffectiveFrom/RawEffectiveTo. Registered ownership is never substituted. Source totals/order counts reconcile exactly; incentives use own order shares. Scheme applies once per rider/app after combining accounts. Category/days/eligibility metrics must agree across that rider's accounts. Vehicle periods use imported assignments and owned/leased car/bike enum evidence; unsupported types block. Overlapping periods are merged, rent charged once per rider/month across apps.
`POST /api/pay/cycles/{id}/advance {stage:1..7}` accepts exactly the next stage. Gates: invoice review → approved upload → account/terms → actual operators → signed scheme/evaluation → monthly adjustments/debts → merged net → independent FIN approval. Every transition is audited with advancedBy. The final checker must be independent of the creator and all preparers. Source changes invalidate the draft. `action:cancel` preserves an unapproved cycle and permits a new draft. Missing evidence and negative results are `needs_decision`; no automatic debt. Every adjustment needs a target counterpart. Existing debt/tag sources are reused once per rider/month, with balances updated through Debts.Post only at final approval.
Approval posts platform receivable, principal/agent income,212103 payable, VAT, explicit rent/recoveries and company costs in one transaction; each line retains platform, account references, rider, period and source. Posting gates and closed periods apply. Already posted/reversed invoices and duplicate legacy/new runs are blocked. Bank preview includes the actual closing2110/212103 liability. Immutable old runs/journals remain readable.
Corrections use `action:reversal_request` with an open `period` and `note`, then an independent `action:reversal_approve`. Original journals/ledgers remain intact; append inverse journals and ledger reversal evidence. Debt snapshots restore only if no later debt activity occurred; later cycles or already paid liability block reversal. A replacement cycle explicitly supplies `replacesCycleId` and posts in the reversal period. GET cycles and lines are scoped/paginated; line filters accept app/rider.

For apps without a spreadsheet adapter, each cycle invoice may instead supply `invoice:{reference,sourceSha256,amountExclVat,vat,deductionsTotal,lines:[{lineId,accountId,baseGross,incentives,orders,deductionAmount}]}`. Review sourceLineId values refer to these upload lineId keys. This is an explicit normalized manual upload, not an automatic spreadsheet interpretation. Source SHA and reference are reviewed by the checker. Source lines and totals reconcile, store as cycle_pending, and become approved only with independent stage7. Existing approved source rows remain unchanged. Raw HS invoices lacking a reviewed deductionsTotal cannot silently mean zero; normalize/reconcile them first.

## Operations read API
`GET /api/operations/{kind}` always returns `{items,total,page,pageSize}`; q/sort/pageSize follow the shared pagination contract (maximum200). Kinds: city,housing,housing_residence,vehicle,vehicle_assignment,custody_handover,sponsorship_period,legal_case,platform_account. `operations.view` plus company/platform/parent scope is checked before search/paging. Unknown companies require all-company scope. Nested source payloads are not exposed; housing returns structural rooms and omits external occupants. `GET /api/riders/{iqama}/accounts` uses actual assignment records with RawEffectiveFrom/RawEffectiveTo, not registered ownership. Existing operational/finance role defaults refresh through current permissions without rewriting stored users.

## Monthly rider statement
`GET /api/finance/statement/rider/{iqama}/monthly?period=yyyy-MM` requires pay.view,payroll.view,debts.view and the full company/app/debt scope of the selected cycle. It returns header,cards,deductions,net,carried,closing,source,status,balanceBasis. Admin can review unapproved cycle lines (status preview); no split of a hidden app's monthly aggregate is inferred. Gross is platform gross plus incentive; earnedGross is the internal scheme amount. Rent is allocated once in cards/explain. Balances are explicitly cycle snapshots, not live bank availability. Current posted liability remains the bank-file basis.
`GET /api/rider-mobile/statement?period=yyyy-MM` accepts only an active rider bearer session, derives identity from the stored token, rejects identity override parameters, and returns approved cycles only. Without a matching new path it uses immutable approved legacy run snapshots, never unapproved previews. Legacy lines without proven app context are labelled legacy_unattributed. No whole cycle/source rows, other riders, raw IBAN or debt snapshots are returned; IBAN is masked. Empty approved history is source none. Invalid/expired/inactive tokens return401.
