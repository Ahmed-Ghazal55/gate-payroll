# Ninja invoice adapter (BR31)

All endpoints require authentication, `Ninja` platform scope and the company's financial scope. Reads use `pay.view`; import/classification/dispute use `pay.manage`; approve/resolve/post use `pay.approve`. Approval is strictly independent of the importer and deduction classifiers, including administrators.

`POST /api/platforms/ninja/invoices` accepts multipart fields: `file` (one XLSX, ≤8MiB), `companyId`, `period` (yyyy-MM), `reference`. Default is a read-only preview returning `{rows,canCommit,fingerprint}`. Confirm by resending the **same file and fields** to `?commit=1`, plus `rows` as JSON text, `fingerprint` and `confirm=true`. The signed preview binds actor, file, company, account/terms/invoice state. Duplicate file hashes/references, ambiguous captains, invalid numeric cells, VAT and component mismatches are refused. The supplier's43-column workbook is parsed through NinjaBilling.Reconcile;7 unused optional columns do not become inferred amounts.

`GET /api/platforms/ninja/invoices` supports normal pagination. `GET /api/platforms/ninja/invoices/{id}/lines` returns immutable invoiced facts with `platformAccountId`, `orders`, `baseGross`, `incentives`, `deductionAmount`, `deductions`, `expected`, `invoiced`, `difference`, `reason`, `status`. The account is resolved from Ninja CaptainId, never from a name. Amounts are net of VAT; VAT stays with the company. Component rounding residual is explicit and the final amount always equals the invoice.

The record begins `invoiced` (engine values before the invoice are only expected). `POST …/{id}/approve` sets invoice and lines `final`/approvalStatus=approved. Expected differences never create a dispute and never block approval/posting. An edited BIKE label records `vehicle type edited by the platform`; the invoiced amount is used. Other differences use a neutral reason, without pretending the cause is known.

Before approval classify each negative component using `POST …/{id}/classify` with `{lineId,category,level,expenseAccount?}`. Level is company_level (active expense account required) or account_level (actual rider is assigned later through payroll, never inferred from the account owner). Penalty/Naqil/stops and supplier adjustments retain their signed invoice source. Supplier-only adjustments must be company_level. Confirmed `platform_deduction` records preserve classifications without creating debts.

Payroll cycle review accepts `sourceCategory` on a deduction to split multiple components of one source line. Each component must match the approved source amount, classification and company cost account; an account-level component must match its original platform account. Do not submit both a line total and its components. Existing unsplit HS/manual invoice contracts stay compatible.

Optional formal dispute: `POST …/{id}/dispute {reason}`; independent `POST …/{id}/resolve {disputeId,reason}`. These are deliberate disputes, distinct from expected differences. Open formal disputes block accounting and payroll use. Resolution preserves invoiced facts; credits/corrections need the accounting reversal/correction workflow.

`POST …/{id}/post` uses the Ninja posting switch (off by default), active target accounts112806/411104/213201 and an open accounting period. It refuses any invoice already reserved by a payroll cycle, preventing duplicate revenue. Company deductions debit their classified cost and credit the receivable. Account-level deductions require actual rider allocation in the payroll cycle, so direct invoice posting refuses them. Normally approve the invoice, then post the complete entitlement and deductions **through the payroll cycle**; standalone posting is an alternative, not an additional step.
