# Internal financial voucher numbers (BR30)

Ghazal provisions a random32–256character `Vouchers__Secret` in MonsterASP server environment settings **before enabling financial writes**. Do not put it in Git or client code. If absent, new numbered financial documents refuse with503; startup/read-only use remains available. Synthetic tests configure their own test-only key. The agent never reads the actual value.

`voucherNo` is server-owned: `PV|RV|JV|AV-yyyy-sequence-check`, sequence minimum6digits and an8hex-character HMAC-SHA256 check over **company + type/year/sequence**. Sequences are independent per company/type/year. The sequence, index and business record commit in the same transaction and the Store distributed write lock; rollback consumes nothing. Cancelled documents keep their numbers. Numbers, company/year and historical Odoo references cannot be changed after issue.

Coverage: all new company-owned posted journals (JV), manual drafts (JV, shared with their final posted journal), advance requests (AV), advance payout vouchers (PV, returned as `payoutVoucherNo`), payroll payment ledger documents (PV), debt receipts (RV; payroll netting is JV) and platform invoices (JV). Existing financial journals therefore retain a journal number alongside the operational document's voucher number. Historical/unassigned records and snapshot imports are not renumbered. Cutover refuses two colliding documents bearing different issued numbers; it never guesses how to remap them. Neither cutover mode triggers new issuance.

`odooVoucherNo` is optional historical input on manual journals, advance requests/payouts, payments, collection receipts, Ninja import and normalized payroll invoice uploads. It is unique case-insensitively per company and counterparty (rider, explicit counterparty, or company). A same-entity duplicate refuses the entire transaction; reusing an existing request/approval does not allocate again. Both references are searchable in authenticated `GET /api/search?q=...`, under the same company/financial/record permissions as their original screen.

Public `GET /api/vouchers/verify/{no}` has a separate30requests/IP/minute limit, returns exactly `{status,type}`, and discloses no amount, party, company, actor or internal IDs. Unknown/altered/unregistered numbers return status=invalid/type="". It checks the durable issued-number index and its current owning document; cancelled and reversed numbers remain verifiable. Issued numbers remain registered if the HMAC secret is rotated; new issuance uses the new secret. Back up both the business records and voucher metadata together.

**QR payload for Antigravity:** absolute URL = the site's public origin + `voucherVerifyUrl`, e.g. `new URL(document.voucherVerifyUrl, window.location.origin).href`. The relative URL is `/api/vouchers/verify/<URL-encoded voucherNo>`. The secret/HMAC input and source IDs never enter the QR. Authenticated screens show document amounts separately; the public response intentionally shows only status/type.
